## Findings

1. **Critical — The force-close test can pass without producing a valid HTLC claim transaction.** It only asserts that the HTLC package is nonempty, while neither it nor the anchor leg verifies descriptor spends, known wallet inputs, signatures, or achieved feerate ([release_contract.rs:312](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:312), [release_contract.rs:330](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:330), [common/mod.rs:333](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:333)). LDK trusts the transaction returned by `WalletSource::sign_psbt` and broadcasts it without script validation (`v0.2.4:lightning/src/events/bump_transaction/mod.rs:1137-1182`). A correctly sized but invalid wallet signature, wrong HTLC spend, or underfunded claim could therefore remain green. Fix: assert descriptor outpoints, known external UTXOs, v3/locktime, witnesses, signatures, and target package feerate for both bump legs.

2. **Critical — The claimed empty-funding-witness panic is not pinned.** Every bridge transaction unconditionally receives a nonempty dummy witness ([common/mod.rs:1039](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:1039)), so removing LDK’s outbound empty-witness panic at `v0.2.4:lightning/src/ln/channel.rs:6406-6414` would leave all nine tests green despite the commit and plan claiming this as a pin. Add an isolated negative test asserting the exact panic, or stop claiming this behavior is release-pinned.

3. **Important — The acceptor’s final zero-fee channel type is not actually asserted.** `server_channel_type` comes from the funder’s `OpenChannelRequest` proposal ([common/mod.rs:1077](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:1077)); the server’s later `ChannelPending` ignores `channel_type` ([common/mod.rs:1156](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:1156)), contrary to the test’s “both sides” comment ([release_contract.rs:35](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:35)). Extract and assert the acceptor’s final `ChannelPending.channel_type`, ideally also checking both nodes’ `ChannelDetails`.

4. **Important — Funding unconfirmation proves only that some `ChannelClosed` event appears, not the required force-close outcome.** The test neither identifies the channel nor asserts removal, unusability, closure reason, monitor update, or commitment bump handoff ([release_contract.rs:345](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:345)). LDK’s own test asserts unusability, empty relevant-tx state, channel removal, monitor update, and broadcast (`v0.2.4:lightning/src/ln/reorg_tests.rs:290-316`). Assert those states plus a `ChannelClose` bump event spending the virtual funding outpoint.

5. **Important — The gate’s negative assertion is both porous and overbroad.** Client and server are observed in sequential three-second windows, so a late client `ChannelReady` during the server window can remain queued; only `list_usable_channels`, not `ChannelDetails.is_channel_ready`, is checked, while any unrelated event causes failure ([release_contract.rs:56](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:56), [common/mod.rs:965](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:965)). Observe both receivers concurrently for `ChannelReady`, assert `is_channel_ready == false`, and explicitly drive relevant timer ticks/pump barriers before confirming.

6. **Important — The cooperative-close test omits two MR-0 claims: reverse payment and capture-before-event durability.** All payments are client/funder → server/acceptor, despite MR-0 requiring both directions ([release_contract.rs:92](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:92), [plan:312](/home/greg/bitcoin-dev/cleanroom/boats/docs/plans/2026-07-29-stage1-bark-upstreaming-plan.md:312)). It also checks only eventual in-memory capture after receiving `ChannelClosed` ([release_contract.rs:129](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:129)); a capture occurring after event availability would pass, and `Mutex<Vec<_>>` proves no durability. Add an acceptor-to-funder payment and sequence instrumentation proving capture precedes event handling; describe persistence durability separately unless crash-tested.

7. **Important — No test covers virtual confirmation at an already-historical anchor height without advancing the real tip.** Every open uses `mine_block`, which invents a new block containing the funding transaction and advances both nodes’ best blocks ([common/mod.rs:829](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:829)). This misses the upgrade case required by the protocol, where an existing anchor may be deeply confirmed and the best-chain view must remain unchanged ([08-channels.md:101](/home/greg/bitcoin-dev/cleanroom/boats/08-channels.md:101)). Advance the real tip first, feed the virtual funding at an older stored header/height, and assert `current_best_block()` remains the real tip while readiness and payment succeed.

8. **Important — Reload reconstructs `KeysManager` with the same start time, contrary to v0.2.4’s API contract.** The harness says seed and time must be identical ([common/mod.rs:388](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:388), [common/mod.rs:457](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:457)), but LDK requires a unique start time for every instance/reload (`v0.2.4:lightning/src/sign/mod.rs:1981-1992`). Because the child counter resets and the start time is embedded in new channel key IDs (`:2453-2466`), copying this can reuse channel keys. Keep the seed/config stable but use a new deterministic test timestamp and prove existing state still reloads.

9. **Important — Restart is not lifecycle-fenced before the advertised chain resync.** The old pump is aborted without awaiting termination, peer transport teardown is not observed, and the new pump plus `timer_tick_occurred` start before the caller’s `refeed_to` ([common/mod.rs:447](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:447), [common/mod.rs:547](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:547), [release_contract.rs:456](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:456)). `ChannelManagerReadArgs` requires monitor/manager synchronization and registration before other manager methods (`v0.2.4:lightning/src/ln/channelmanager.rs:16529-16556`). Return a dormant restored node, complete/await teardown and chain sync, then start the pump and reconnect.

10. **Important — SCID restart stability is tested only for the inbound server; the client assertion is tautological.** Only `server` is reconstructed ([release_contract.rs:448](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:448)), while `new_client_scid` is read from the untouched manager ([release_contract.rs:485](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:485)). A funder/outbound-only deserialization regression passes. Parameterize the test over each role or restart both nodes.

11. **Important — The SCID tests do not pin the protocol’s unannounced, alias-only wire behavior.** Configuration does not explicitly disable announcement or enable `negotiate_scid_privacy` ([common/mod.rs:705](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:705)), and the disagreement test uses only a direct first-hop payment ([release_contract.rs:516](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:516)). In v0.2.4, scid privacy enters the channel type only when configured (`channel.rs:14384-14415`), while outbound direct routing prefers the local real SCID (`channel_state.rs:489-510`). Explicitly configure and assert `is_announced == false`, aliases, and both nodes’ SCIDs; add a route-hint or three-node forwarding test that must use the alias.

12. **Important — Collision-test cleanup races a poisoned manager and globally suppresses unrelated panic diagnostics.** The process-global hook is replaced while other tests can run ([common/mod.rs:981](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:981)), and the pump is aborted only after the panic and never awaited ([release_contract.rs:576](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:576)). The exact panic payload check is sound, but cleanup is not deterministic. Stop and await the pump before provoking the synchronous panic, and avoid the global hook or isolate the test.

13. **Minor — Test-only scaffolding still contains upstream polish debt.** The file-wide dead-code allowance hides unused helpers/fields ([common/mod.rs:8](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/common/mod.rs:8)); `env_logger` and currently `log` are unused ([Cargo.toml:15](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/Cargo.toml:15)); public aliases lack documentation; and comments retain planning language such as “growing contract” and “ONLY IF CHEAP, per the maintainer” ([release_contract.rs:415](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:415), [release_contract.rs:551](/home/greg/bitcoin-dev/cleanroom/bark-stage1/bark-channels/tests/release_contract.rs:551)). Also mark fixed `PeerManager` entropy/time as deliberately insecure test data—v0.2.4 requires CSPRNG bytes and an increasing counter (`peer_handler.rs:1297-1308`).
